---
name: Story pipeline architecture
description: Durable rules for Telegram story batches, per-channel variants, and single-background rendering.
---

Истории в Telegram должны оставаться отдельной веткой, а не переиспользовать `chat_day`: пакет и варианты хранятся в БД, каждый канал получает свой проект и job, а готовые строки `generated_images` с одним общим storage path не запускают image-generation. Выбранный баннер передаётся в renderer через metadata проекта.

**Why:** `chat_day` жёстко рассчитан на пять чат-роликов, а история требует количества вариантов по каналам, отдельной озвучки и пользовательской проверки каждого MP4.

**How to apply:** Новые действия истории привязывать к `story_batches`/`story_batch_items`; постоянное состояние не держать в in-memory maps, а визуальный баннер добавлять только через story-specific renderer parameters.

AI может вернуть корректный по форме сценарий с неправильной суммой длительностей сцен. Перед строгой проверкой нужно нормализовать положительные целые длительности до целевой длины, а для уже сохранённого failed-варианта оставлять повторный запуск из Telegram.

**Why:** Один такой ответ ранее остановил только один канал из batch, из-за чего пользователь увидел меньше вариантов и не мог восстановить его без нового batch.

**How to apply:** Ошибка одного канала не должна блокировать остальные; сохраняй failed item в БД с callback retry и показывай статусы незавершённого batch через меню.

Story-проект нельзя отправлять в legacy `video:review:approve` flow с ручным вводом SEO-данных; при старом callback нужно определить story item по `projectId` и открыть story-публикацию. Повторные approve после публикации должны быть идемпотентными.

**Why:** Telegram сохраняет старые inline-кнопки в сообщениях, поэтому пользователь может нажать устаревший callback уже после изменения или публикации статуса.

**How to apply:** На review/approve callback сначала проверяй связанный `story_batch_item`, его чат и статус; для опубликованного варианта показывай существующую ссылку, не запускай новый manual metadata flow.

Для раздела «История» пользователь ожидает пакетную публикацию: сначала подготовить все выбранные каналы, с уникальными SEO-данными и одним сохранённым channel-specific визуалом на вариант, затем одной кнопкой загрузить весь пакет.

**Why:** Проверка каждого MP4 и ручной ввод метаданных по одному каналу создают путаницу и приводят к публикации не того варианта.

**How to apply:** Не смешивай story batch с обычным роликом; массовое действие должно сохранять канал, заголовок, описание, хэштеги и собственную картинку/аватарку каждого item, используемую на всём его ролике.

Истории с ручным сценарием не должны получать fallback-сюжет при таймауте AI: сохраняй failed item и предлагай повтор, а общий video monitor не должен восстанавливать story jobs как обычные Telegram-ролики.

**Why:** Fallback уже создал формально валидный, но непредсказуемый вариант, а общий recovery monitor мог повторно подхватить отменённый story job после перезапуска.

**How to apply:** Для manual story flow ошибка генерации должна останавливать только конкретный вариант; отменённые/completed story batch и story project IDs исключай из legacy pipeline recovery и delivery loops.

Ручной story flow должен идти в порядке «каналы → общее название → исходный сценарий», а генерация должна быть строго последовательной: следующий канал стартует только после готового MP4 предыдущего.

**Why:** Пользователь проверяет варианты по очереди и не хочет параллельных jobs, которые усложняют согласование и могут смешать результаты каналов.

**How to apply:** После успешного первого item переходить к следующему; при ошибке останавливаться на текущем item, показывать повтор и продолжать оставшиеся каналы только после успешного retry.

Первый ручной канал собирается из исходного текста без AI-сценариста; AI нужен только для альтернативных вариантов следующих каналов.

**Why:** AI-сценарист может превысить сетевой timeout ещё до запуска первого видео, а первый вариант обязан сохранять пользовательский сценарий и не должен зависеть от внешней редакторской генерации.

**How to apply:** Для первого item сохранять полный исходный текст в сценах; для следующих items использовать адаптацию только по этому исходнику и не подставлять новый сюжет при ошибке AI.
